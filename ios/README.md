# BLE pilot v2 — два ESP32-C3 и iOS

## Прошивки

### Плата №1 — iBeacon
Папка `esp32-ibeacon/` — самостоятельный PlatformIO проект.
- iBeacon UUID: `F47D8F33-25FA-4DC8-92CB-8BE1199A6410`
- Major: `1`, Minor: `1`
- **API beacon_id**: `ibeacon:F47D8F33-25FA-4DC8-92CB-8BE1199A6410:1:1`
- Только BLE advertising (без GATT и без Wi-Fi). Интервал ~160 мс.
- TX Power поле -59 dBm является тестовым значением, а не калибровкой расстояния.

### Плата №2 — GATT
Папка `esp32-gatt/` — самостоятельный PlatformIO проект.
- BLE Service UUID: `c6ec1c8d-e23a-4751-93f8-31d4d4a17b10`
- Read characteristic UUID: `c6ec1c8d-e23a-4751-93f8-31d4d4a17b11`
- **API beacon_id**: `gatt:parking-01` (UTF-8 значение READ характеристики)
- Подключение не требует Bluetooth pairing / PIN. После потери связи ESP32 продолжает advertise.
- Интервал advertising ~160 мс. Одновременная работа с многими телефонами не тестировалась.

Открыть **каждую папку отдельно** в VS Code + PlatformIO, Build → Upload. Файлы прошивок не заменяют исходный первый прототип в `esp32/`.

## iPhone приложение

Последний успешный запуск [GitHub Actions Build iOS BLE Probe](https://github.com/zhalenik/parking-ble-test/actions/workflows/build-ios.yml) выдаёт `ParkingBLEProbe-iOS-Xcode-Project` с готовым `.xcodeproj`. Xcode: выбрать Personal Team, подписать и установить на физический iPhone (Run). GitHub Actions собирает *только unsigned Simulator app*, не устанавливаемый на физический телефон.

В приложении отдельно включаются:
1. **iBeacon · Core Location:** `startMonitoring(for: CLBeaconRegion)`, требуется разрешение «Всегда» (Always). Событие `IBEACON_ENTER` может вызвать тестовый POST, `IBEACON_EXIT` только логируется. `IBEACON_STATE INSIDE` не открывает доступ — это лишь состояние при регистрации.
2. **GATT · Core Bluetooth:** скан по Service UUID, первое соединение, чтение `beacon_id`, `GATT_CONNECTED`, затем системный **pending reconnect** после отключения. При новом соединении и успешном чтении ID — тестовый POST. Для тестов нужен Bluetooth permission. Парный PIN не требуется.

## Настройка POST в iOS

В экране приложения:
- Адрес: **полный HTTPS URL** (например `https://example.org/api/mobile/beacon-event`)
- Токен: персональный token клиентской ссылки GateBot, один раз вводится и сохраняется в Keychain (AfterFirstUnlockThisDeviceOnly). Пустое поле при следующем сохранении оставляет токен неизменным.
- `Автоматически отправлять POST` — **по умолчанию выключено**. Включайте только после создания безопасного диагностического endpoint.
- `Отправить ручной TEST POST` — посылает `source=manual`, `event=test` независимо от флажка автосрабатывания; обработчик сервера не должен открывать ворота по такому запросу.
- Общий cooldown для двух механизмов: **60 секунд**. После отправки подавляются другие автоматические запросы, даже если пришли от второй ESP32. Он переживает перезапуск приложения. Повторные HTTP-запросы при ошибке не запускаются автоматически.

Пример тела POST:
```json
{
  "token": "CLIENT_LINK_TOKEN",
  "beacon_id": "ibeacon:F47D8F33-25FA-4DC8-92CB-8BE1199A6410:1:1",
  "source": "ibeacon",
  "event": "enter",
  "request_id": "19b94866-b88b-4937-8a0f-3915c5bc3a86",
  "occurred_at": "2026-11-25T11:21:32.457Z"
}
```
Для GATT: `source=gatt`, `beacon_id=gatt:parking-01`, `event=connected`. Для ручного теста: `source=manual`, `beacon_id=test:manual`, `event=test`.

Headers: `Content-Type: application/json`, `Accept: application/json`. Токен идёт **в теле**, а не в Authorization header. Пользовательские токены не должны попадать в серверные логи, если логируется исходный JSON.

Пример безопасного тестового ответа:
```json
{"status":"logged","message":"Test event recorded"}
```
Ответ HTTP 200/202. Приложение логирует только `http`, `rtt_ms` и краткое `status` из JSON, без токена и без тела ответа. Ошибки подключения и HTTP-статусы фиксируются.

## Минимальная доработка GateBot (выполняется ВРУЧНУЮ, НЕ в этом репозитории)

1. Добавить отдельный `POST /api/mobile/beacon-event` поверх **HTTPS**, не переиспользовать `/open-gate` для этого испытания.
2. Принять поля `token`, `beacon_id`, `source`, `event`, `request_id`, `occurred_at`. Проверить длину и тип полей. Не принимать от телефона `button_id`, номер шлагбаума или `branch_id`.
3. В БД GateBot связать **оба beacon_id** с одним `branch_id + stable_id` ворот. При необходимости поддержать сопоставление одной метки с несколькими филиалами, но не создавать неоднозначных команд.
4. Найти пропуск по `token`, проверить принадлежность к филиалу, действительность, часы доступа, запреты и подписку по существующим правилам `AccessService`. Не менять текущие проверки допуска.
5. На этом этапе **ТОЛЬКО записать диагностическое событие**, НЕ обращаться к телефонной очереди и НЕ открывать ворота. Вернуть JSON `{"status":"logged"}` или ошибку `{"status":"denied"}`. Учитывать `request_id` как ключ идемпотентности, чтобы возможные повторные доставки не создавали дубликатов.
6. Когда эксперименты завершатся, открытие следует проводить исключительно через существующий `AccessService` и одну очередь; никакого прямого вызова модема из нового endpoint.

## Полевая программа

- Установить две ESP32 в разные USB-питания, достаточно разнести на 1–2 метра для начала.
- iPhone разрешить Bluetooth и **Always Location**. Если iOS показала только «При использовании», вручную перевести приложение в «Всегда» через Settings → Privacy & Security → Location Services.
- При включенном мониторинге и выключенном autoPOST проверить по журналу `IBEACON_ENTER/EXIT` и `GATT_ID_READ / GATT_DISCONNECTED / GATT_PENDING_RECONNECT`.
- Настроить тестовый endpoint, нажать «Отправить ручной TEST POST», проверить лог `HTTP_RESPONSE`. Только потом включить автосообщения.
- Переместить iPhone за пределы устойчивой дальности обоих маяков, выдержать время, вернуться. Контрольные точки: 15 минут, 12 часов, 24 часа, 3 суток.
- Убедиться, что запросы по каждому методу действительно появляются *после долгого отсутствия*, а не только сразу после настройки приложения.

### Ограничения

- iBeacon может не выдать новый вход без предыдущего устойчивого выхода из области; задержки и расстояния не детерминированы.
- GATT восстановление после принудительного закрытия iOS-приложения свайпом не гарантировано; простая перезагрузка — отдельный тест.
- Подключение к GATT не гарантирует близость автомобиля и не доказывает подлинность метки.
- Бесплатно подписанный Personal Team билд iPhone обычно требует повторной установки через 7 дней.
- Сетевое выполнение в фоне ограничено iOS; таймеры и постоянный WebSocket для этой цели не подходят.
- Размещение оборудования на чужой территории требует разрешения собственника.

## Что проверять после первого теста (v2.1 ESP32)

При включении iBeacon-мониторинга рядом с передатчиком `IBEACON_STATE INSIDE` — это **успешное обнаружение**. `IBEACON_ENTER` при включении мониторинга внутри зоны не обязан появляться: сначала должна быть зафиксирована граница OUTSIDE, потом новый вход. `authorized=3 regions=1` означает разрешение Always и одну зарегистрированную область, а **не один обнаруженный маяк**.

При GATT-сканировании `GATT_SCAN_START` означает только регистрацию поиска. Нужны `GATT_DISCOVERED → GATT_CONNECTED → GATT_ID_READ`. Если их нет, проверь, что прошит новый `esp32-gatt`: в v2.1 рекламный пакет содержит **только Flags и Complete 128-bit Service UUID** (21 байт) в основном ADV; прежняя версия пыталась разместить имя вместе с 128-bit UUID и могла превысить 31 байт.

Начиная с новых прошивок:
- Wi-Fi выключен командой `WiFi.mode(WIFI_OFF)`.
- BLE TX установлен `ESP_PWR_LVL_P0` (примерно **0 dBm**, не максимум).
- Встроенный голубой LED ESP32-C3 SuperMini (GPIO8, active LOW) кратко мигает раз в ~2.2 с в обоих проектах; при GATT-соединении мигает примерно раз в 0.65 с. На некоторых клонах разводка LED может отличаться. GPIO8 — boot strap, поэтому конфигурируем его только после BLE init.
- Во время теста iBeacon не ориентируйся на момент нажатия Start, если телефон уже лежит рядом. Зафиксируй сначала `IBEACON_EXIT` вдали, затем возвращайся и ищи `IBEACON_ENTER`. Задержка может быть большой.
- Для GATT после обновления ESP32 в приложении нажми `Забыть сохранённый GATT и искать заново`. Если после этого нет обнаружения даже в активном приложении, проверь передатчик через приложение-сканер nRF Connect и наличие UUID `C6EC1C8D-E23A-4751-93F8-31D4D4A17B10`.

Пока нет безопасного диагностического POST endpoint, автоматическую отправку держи выключенной. `IBEACON_STATE INSIDE` лишь логируется и **не вызывает POST**, это сделано намеренно.
